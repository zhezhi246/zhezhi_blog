## 二、调整原规划的原则

1. **先做工程，再堆技术名词。** 比起同时学 CUDA、vLLM、SFT、TensorRT，更需要独立完成一个可编译、可运行、可复现的 C++ 项目。
2. **优先补科研编程的短板。** CMake、Linux、GDB、内存管理、异常与资源清理、Git、单元测试，比当前阶段的高级模板技巧更重要。
3. **避免“跑通 Demo = 掌握推理优化”。** 需要解释精度误差、显存占用、纯推理耗时与端到端耗时，并有工具支持的瓶颈分析。
4. **保留数学与 GNN 的优势。** 在量化、数值误差、动态图和不规则访存方面形成个人特色，而不是完全重启一个陌生方向。
5. **学习与求职并行。** 有可展示的 MVP 后就开始投递、复盘面试，再决定项目需要补什么。
6. **科研底线不能失守。** 需要给课题、毕业要求预留稳定时间，避免因求职准备反而影响按时毕业。

## 三、分阶段执行计划

### 阶段 A：2026 年 11 月—12 月上旬｜C++ 工程基础

**目标：** 从“看懂 C++ 语法”转到“能构建、调试、维护 C++ 小项目”。

**必学内容**

* C++11/17 基础：引用、指针、`const`、STL 容器、迭代器、函数与类。
* 资源管理：RAII、智能指针、移动语义、拷贝与移动的区别。
* Linux：命令行、编译链接、文件系统、环境变量、基本脚本。
* 工程：CMake、Git、GDB、编译警告、Sanitizer、基本单元测试。
* 算法题：数组、哈希表、双指针、二分、链表、栈与队列；保证规律性，不追求刷题数量。

**实践任务**

* [ ] 使用 CMake 完成一个多文件 C++17 项目。
* [ ] 使用智能指针或自定义 RAII 类管理资源。
* [ ] 独立定位一次真实的编译错误或运行错误，并写下调试过程。
* [ ] 为至少一个函数添加基本测试。
* [ ] 通过持续练习建立 LeetCode 常见题型的解题习惯。

**阶段产出**

`cpp-engineering-basics` 小仓库：包含源码、CMakeLists.txt、README、构建步骤、测试命令。

**验收标准**

> 能在干净环境中依据 README 编译运行；能用 GDB 和 Sanitizer 定位常见问题；能解释 RAII 如何减少内存或资源泄漏。

### 阶段 B：2026 年 12 月中下旬—2027 年 1 月｜ONNX 与 C++ 推理入门

**目标：** 独立实现模型推理，而不是只使用 Python 脚本导出模型。

**学习内容**

* ONNX 的计算图、输入输出、静态与动态形状、导出和验证。
* ONNX Runtime C++ API；OpenCV；C++ 推理程序的组织方式。
* YOLO 预处理（如 Letterbox / Normalize / HWC→CHW）、推理输出解析与 NMS。
* CUDA 入门在 C++ 推理基线稳定后进行：Kernel 启动、线程组织、设备内存、同步和 CUDA Events；允许顺延至 TensorRT 阶段。

**实践任务**

* [ ] 从 PyTorch 导出 ONNX，核对输入输出和输出数值。
* [ ] 完成纯 C++ ONNX Runtime 推理程序。
* [ ] 实现并验证预处理、输出解析、NMS。
* [ ] 使用固定图片集比较 Python / C++ 输出是否一致（允许合理浮点误差）。
* [ ] 写 1—2 个简单 CUDA 示例（如 Vector Add、Reduction），不追求复杂优化。

**阶段产出**

具备完整输入 / 预处理 / 推理 / 后处理的 C++ Demo；能记录单步耗时。

**本阶段不优先做**

* SFT / LoRA 训练；
* 大量 LLM 框架横向学习；
* 从零实现 FlashAttention；
* 大型 vLLM 源码改造。

### 阶段 C：2027 年 1—2 月｜TensorRT 旗舰项目 MVP

**目标：** 在 NVIDIA GPU 上构建可复现的 C++ TensorRT 推理项目，并形成简历 v1。

**核心任务**

* [ ] 完成 ONNX → TensorRT Engine 的构建与加载。
* [ ] 用 C++ 实现 Engine 推理、CUDA Buffer/Stream 管理、动态形状（按实际模型需要）。
* [ ] 实现或复用经过验证的后处理，并记录端到端结果。
* [ ] 比较参考浮点模型与 FP16 推理的精度和耗时。
* [ ] 完成 `README.md`、构建脚本、环境说明、基础性能表。
* [ ] 提炼 2—3 条可解释的项目简历描述。

**项目名称建议**

`High-Performance YOLO Inference Engine`
基于 C++、ONNX Runtime、TensorRT、CUDA 的目标检测推理及性能分析项目。

**MVP 验收标准**

1. 输入真实图像，输出可视化检测结果；
2. 不依赖 Python 推理入口，能够运行 C++ 推理程序；
3. 能重现至少两种执行配置的正确性与速度比较；
4. README 包含硬件、驱动、CUDA、TensorRT 版本和可复现步骤；
5. 能向面试官解释模型的输入输出、数据转换和资源生命周期。

> 本阶段只要求完成 MVP，不要求把 INT8、CUDA 性能优化与全部实验一次做完。若 ONNX Runtime 基线尚未稳定，先完成基线，再启动 TensorRT。

### 阶段 D：2027 年 2—3 月｜量化、Profiling、实习投递

**目标：** 从“会部署”向“会分析优化”迈进，同时真正开始求职。

**技术任务**

* [ ] 学习对称 / 非对称量化、scale / zero point、Per-tensor / Per-channel、PTQ 与 QAT。
* [ ] 理解 MinMax、基于直方图的 KL 校准及离群值对精度的影响。
* [ ] 使用**与当前安装版本兼容**的量化工具构建 INT8 模型，优先了解显式 Q/DQ 工作流。
* [ ] 按相同数据和测试条件比较 FP32 / FP16 / INT8 精度与性能。
* [ ] 学习 Nsight Systems、CUDA Events 等，定位一个可复现的瓶颈。
* [ ] 完成至少一次优化尝试，保留优化前后原始数据和失败记录。

**量化版本提醒**

TensorRT 的量化 API 随版本演化：旧式隐式 INT8 Calibrator 在新版中逐步弃用并移除。**原理仍要学，但新项目不要依赖已经移除的旧接口。**实际实现以所选 TensorRT / ModelOpt 版本官方文档为准，优先研究 ONNX Q/DQ 显式量化流程。

**求职任务**

* [ ] 简历 v1 完成，并针对“部署 / AI Infra / 算法工程化”调整关键词。
* [ ] 整理项目常见问答：为什么用 FP16、INT8 如何校准、CPU/GPU 瓶颈如何区分、Benchmark 如何保证公平。
* [ ] 建立岗位投递表：公司、岗位、城市、投递时间、技术要求、面试反馈。
* [ ] 持续投递 2028 届暑期实习；根据各公司发布节奏动态调整。

**验收标准**

> 至少有一份能公开展示的 Benchmark 报告，并能用实际数据回答：“性能瓶颈是什么？做了什么改动？改进是否有效？有没有带来精度或显存代价？”

### 阶段 E：2027 年 4—5 月｜补短板、面试强化、扩大机会

**目标：** 根据反馈弥补能力短板，而不是继续无限扩展新框架。

* [ ] 复习 C++、Linux、数据结构、操作系统、计算机网络中与岗位相关的高频基础。
* [ ] 深入掌握 CUDA 内存模型、异步执行、同步、带宽与计算瓶颈。
* [ ] 复盘每次笔试和面试，记录问题及补救动作。
* [ ] 如果暑期实习机会有限，增加日常实习、中小型 AI 公司、机器人 / 工业视觉公司投递。
* [ ] 视主项目成熟度，开始了解 LLM 推理：Attention、KV Cache、Prefill / Decode、Continuous Batching。

**验收标准**

能在白板或共享屏幕条件下解释主要代码结构、瓶颈、量化实验、常见 C++ 基础问题，而不是只能展示运行截图。

### 阶段 F：2027 年 6—8 月｜企业实习 / 工程积累

**目标：** 尽量接触真实代码库、真实模型、真实线上或端侧性能问题。

## 四、旗舰项目的建议技术方案

### 4.1 项目架构

```text
PyTorch YOLO
    │ 导出、校验
    ▼
  ONNX ──────────────► ONNX Runtime C++（基线）
    │
    ├──► TensorRT Float / FP16 Engine
    │
    └──► PTQ → Q/DQ ONNX → TensorRT INT8 Engine
                         │
                         ▼
                 C++ Runtime / CUDA
                         │
          预处理 → 推理 → NMS → 输出
                         │
                         ▼
             Accuracy + Benchmark
                         │
                         ▼
            Profiling + 优化复测
```

### 4.2 建议仓库结构

```text
yolo-inference-engine/
├── CMakeLists.txt
├── README.md
├── cmake/
├── include/
├── src/
│   ├── main.cpp
│   ├── preprocessing.cpp
│   ├── postprocessing.cpp
│   ├── ort_runner.cpp
│   └── trt_runner.cpp
├── cuda/                    # 后期加入自定义 Kernel
├── scripts/                 # ONNX 导出 / 量化 / 数据准备
├── tests/                   # 预处理和输出一致性测试
├── configs/
├── benchmarks/
│   ├── results.csv
│   └── methodology.md
└── docs/
    ├── accuracy.md
    ├── profiling.md
    └── troubleshooting.md
```

目录仅为建议，可以根据复杂度适当简化。重点是保证代码可维护和实验可复现。

### 4.3 Benchmark 必测项

|类别|指标|注意点|
|-|-|-|
|正确性|输出一致性、检测结果、mAP50-95|使用独立评估集；记录不同精度下的差异|
|模型级性能|GPU 推理延迟、吞吐量、显存|固定模型、输入形状、batch、预热与测试条件|
|端到端性能|解码、预处理、H2D、推理、D2H、NMS、总延迟|明确是否包含所有阶段|
|延迟分布|Mean、P50、P95、P99|固定足够的请求次数并说明计时方式|
|环境|GPU、驱动、CUDA、TensorRT、编译器、功耗设置|确保结果可比较|

**一项合格的性能优化记录至少包含：**

1. 原始问题和复现方法；
2. Profiling 证据与瓶颈假设；
3. 代码改动；
4. 优化前 / 后的正确性、延迟、吞吐、显存对比；
5. 不适用情况和局限性。

> 如果 INT8 没有更快，或者 CUDA 预处理使延迟变差，也应如实记录并分析。严谨的失败实验比没有测量依据的“加速 X 倍”更有价值。

### 4.4 硬件条件对应路线

* **有兼容 NVIDIA CUDA GPU：** 先做本机 C++ + TensorRT；有条件再考虑 Jetson 端侧复现。
* **暂时没有 NVIDIA GPU：** 先做 ONNX Runtime C++（CPU 或受支持的执行后端）、精度验证和 Benchmark；等硬件可用后再做 TensorRT / CUDA 实验。
* **目标是 RK3588 等 NPU：** 后续补设备对应的工具链（如 RKNN），不要将 NVIDIA TensorRT 经验直接等同于所有边缘平台部署能力。

## 五、差异化副项目（主项目稳定后再开始）

### Crystal GNN Inference Profiling

**目标：** 将科研积累转化成“理解模型且能分析性能”的就业优势。

**候选任务**

* 在已有晶体 GNN 模型上建立不同图规模、原子数、边数和 batch size 的推理测试。
* 使用 PyTorch Profiler 对消息传递、scatter/gather、图聚合和数据搬运等环节分析耗时。
* 对比不同 batch 策略或计算实现；记录精度和性能变化。

**重要限制：** 不预设全部 GNN 算子都可以无缝导出 ONNX 或运行在 TensorRT；先依据使用的算子与版本验证兼容性。这个副项目不是 2027 年初找实习的前置要求。

## 八、暂缓学习与常见风险

### 暂缓项

* **SFT / LoRA：** 当前与主投岗位相关性较弱，除非出现明确的岗位需求。
* **同时深学 vLLM 与 TensorRT：** 先完成一个主项目，再扩展 LLM 推理。
* **高级 C++ 模板元编程：** 目前投入产出比低。
* **过早购买边缘开发板：** 先确认是否有设备需求和实际项目预算。
* **同时做两个大型开源项目：** 第一项目可复现、可维护、可讲清楚后，再启动第二项目。

### 风险与应对

|风险|应对|
|-|-|
|C++ 入门时间超预期|保证 CMake / STL / RAII / 调试，延后 CUDA 高级内容|
|TensorRT 环境与版本踩坑|固定兼容版本，记录驱动与依赖，优先保证 MVP|
|GPU 不可用|先用 ONNX Runtime C++ 完成可验证的工程项目|
|科研任务繁重|每周投入适当缩减，但保持连续、可验收的小产出|
|投递反馈少|扩大岗位层级和公司范围，复盘简历和面试短板|
|被技术热点带偏|每次学习新框架先回答：是否服务当前项目或目标岗位？|

## 九、最终衡量标准

到 2027 年春季，至少应能独立回答：

1. **能否独立完成一个可运行、可维护的 C++ 模型推理程序？**
2. **能否准确解释模型精度、推理延迟、吞吐量和显存占用的实验数据？**
3. **能否使用工具定位一个真实瓶颈，并设计、实现、验证优化？**

如果三点做到，就已经从“以科研代码为主的深度学习研究生”迈向“具备初步 AI 推理工程能力的求职者”。之后应优先通过实习和真实工程环境继续提高，而不是单纯增加学习框架的数量。

**一句话总结：**

> 用 C++ 工程化补齐短板，用 TensorRT / CUDA 推理优化建立技术主线，用数学与晶体 GNN 背景形成差异化，并尽早通过真实招聘反馈校正路线。
